# 项目章程

## 核心原则

### I. 代码质量门禁

所有提交的代码 MUST 通过以下三重检查, 缺一不可:

1. **ESLint 检查**: 代码 MUST 通过 ESLint 静态分析, 零 error, 零 warning.
   配置文件需纳入版本管理, 团队统一规则.
2. **Prettier 格式化**: 代码 MUST 经过 Prettier 格式化, 不允许手动格式覆盖.
   保存即格式化, CI 中强制检查.
3. **TypeScript 类型检查**: 代码 MUST 通过 `tsc --noEmit` 严格模式检查,
   零类型错误. 禁止使用 `any` 类型, 除非有明确理由并以 `// eslint-disable-next-line`
   标注原因.

**理由**: 代码质量门禁是交付可靠软件的基础. 静态分析能在运行前捕获大量缺陷,
格式一致性降低代码审查噪音, 类型系统是 TypeScript 项目的核心安全网.

### II. 测试纪律

代码完成前 MUST 通过以下两级测试:

1. **单元测试**: 对核心业务逻辑、工具函数、API 路由处理函数编写单元测试.
   使用 Vitest 或 Jest 作为测试框架. 测试覆盖率 SHOULD 达到关键路径 80% 以上.
2. **页面级 E2E 测试**: 对用户可见的页面流程编写端到端测试.
   使用 Playwright 作为 E2E 测试框架. 每个用户故事 MUST 至少有一个 E2E 测试用例
   覆盖主要路径.

**理由**: 单元测试保证组件级正确性, E2E 测试保证用户视角的端到端流程完整性.
二者结合才能形成有效的质量防线.

### III. 自校验与生产验证

**核心原则: 看起来没问题不代表 run 没问题.**

代码完成后 MUST 执行以下自校验流程:

1. **构建验证**: `npm run build` MUST 零错误通过.
2. **运行时验证**: 启动 dev server, 在浏览器中实际操作验证功能正常.
3. **Edge Case 测试**: 针对边界条件(空数据、大数据量、并发请求、异常输入)
   MUST 编写测试并验证通过.
4. **问题定位与修复**: 如果发现问题, MUST 定位到具体根因, 修复后重新跑通
   全部检查(lint、类型检查、单元测试、E2E 测试), 直到全部通过.
5. **生产环境模拟**: 代码 MUST 能在模拟生产环境(`next build && next start`)
   下正常运行, 不能仅依赖 dev 模式验证.

**理由**: 开发环境与生产环境存在差异(热更新、错误容忍、环境变量等).
只在 dev 模式通过不代表生产可用. 必须模拟生产环境验证.

### IV. 简洁性与可维护性

1. 代码 MUST 遵循 YAGNI 原则——不实现当前不需要的功能.
2. 组件和函数 SHOULD 保持单一职责.
3. 修复 bug 时 MUST NOT 引入不相关的重构或"改进".
4. 删除功能时 MUST 确认无其他代码依赖后再删除, 不留死代码.

**理由**: 过度设计和不必要的改动是项目复杂度膨胀和回归 bug 的主要来源.

### V. 持续集成

1. 每个功能分支 MUST 在合并前通过完整的质量门禁:
   ESLint + Prettier + TypeScript + 单元测试 + E2E 测试 + 构建验证.
2. 提交粒度 SHOULD 保持小而完整——每次提交解决一个问题或实现一个功能点.
3. 合并前 MUST 确认不破坏已有功能(回归测试).

**理由**: 持续集成确保主分支始终处于可发布状态, 小粒度提交便于问题追溯.

## 技术栈约束

本项目的技术选型 MUST 遵循以下约束:

| 领域 | 技术选择 | 备注 |
|------|----------|------|
| **全栈框架** | Next.js (App Router) | 前后端统一框架, 前端调用后端 API 路由 |
| **语言** | TypeScript (严格模式) | 全部代码使用 TypeScript, 禁止纯 JS 文件 |
| **CSS 方案** | Tailwind CSS | 实用优先的 CSS 框架 |
| **UI 组件库** | shadcn/ui | 基于 Radix UI 的可定制组件 |
| **图表库** | ECharts | 所有图表需求 MUST 使用 ECharts 实现 |
| **单元测试** | Vitest / Jest | 根据项目配置选择 |
| **E2E 测试** | Playwright | 页面级端到端测试 |
| **代码检查** | ESLint | 静态代码分析 |
| **代码格式化** | Prettier | 统一代码风格 |
| **包管理器** | npm / pnpm | 根据项目初始化选择, 保持一致 |

**理由**: 统一技术栈减少决策成本, 降低团队认知负荷,
确保所有代码遵循一致的模式和最佳实践.

## 开发工作流程

### 质量门禁执行顺序

每次代码变更后, MUST 按以下顺序执行验证:

```
1. Prettier 格式化检查  →  npx prettier --check .
2. ESLint 静态分析      →  npx eslint .
3. TypeScript 类型检查  →  npx tsc --noEmit
4. 单元测试             →  npm run test
5. E2E 测试             →  npx playwright test
6. 构建验证             →  npm run build
7. 生产模式验证         →  npm run start (验证关键流程)
```

### 问题修复流程

当任何检查步骤失败时:

1. 定位到具体失败的文件和行号.
2. 分析根因, 不做表面修复.
3. 修复后从步骤 1 重新执行全部检查.
4. 全部通过后方可提交.

### 代码审查要求

- 每个 PR MUST 包含对应的测试(单元测试或 E2E 测试).
- PR 描述 MUST 说明变更内容、测试方法和影响范围.
- CI 全部通过后方可合并.

1. 本章程优先于所有其他开发实践. 当其他文档与本章程冲突时, 以本章程为准.
2. 修正本章程需要: (a) 记录修改理由, (b) 更新版本号, (c) 同步更新所有引用模板.
3. 所有 PR 和代码审查 MUST 验证是否符合本章程的核心原则.
4. 复杂性偏离(如引入额外依赖或绕过测试)MUST 在代码中记录理由.
5. 运行时开发指导参见项目根目录的 `CLAUDE.md` 文件(如存在).
